# BLE MAC Addresses on Nordic Chips (Zephyr / NCS)

> 🌐 [Deutsche Version](../de/ble-mac-addresses.md)

## Address Types

BLE defines two principal address categories:

| Type | Description |
|------|-------------|
| **Public** | Globally unique, IEEE-registered OUI. Burned into hardware by the manufacturer. Nordic nRF52/nRF53 chips do **not** have a factory-programmed public address. |
| **Random** | Generated by software. Subdivided into *Static*, *Private Resolvable* (RPA), and *Private Non-Resolvable* (NRPA). |

## What Nordic Chips Use by Default

Without any explicit configuration, the Zephyr BT stack generates a **Random Static Address** on first boot:

- Bit 47 and 46 of the address are both set to `1` (per BLE spec, §1.3).
- The address is stored in NVS/Settings flash and **survives resets**.
- It looks "random" but is stable for the lifetime of the device (or until flash is erased).

Example from the serial log:
```
Identity: CC:8F:EB:B8:55:B8 (random)
```

## Effect of `BT_LE_ADV_OPT_USE_IDENTITY`

By default, Zephyr uses **Resolvable Private Addresses (RPA)** during advertising to prevent tracking. Setting `BT_LE_ADV_OPT_USE_IDENTITY` in the advertising parameters forces the stack to use the identity address (the Random Static Address) instead:

```c
BT_LE_ADV_PARAM_INIT(BT_LE_ADV_OPT_USE_IDENTITY, ...)
```

For BThome sensors this is the **correct choice**: home automation hubs (e.g. Home Assistant) identify sensors by their MAC address. A changing RPA would be treated as a new, unknown device on every rotation interval.

## Kconfig Options

| Option | Effect |
|--------|--------|
| `CONFIG_BT_PRIVACY=y` | Enables RPA generation (default on). Without `USE_IDENTITY`, advertising uses RPAs. |
| `CONFIG_BT_SETTINGS=y` | Persists the identity address in NVS across resets. |
| `CONFIG_BT_FIXED_ADDRESS` | (Not available on nRF52 without custom HAL) — would allow a hard-coded address. |

## Setting a Custom Address at Runtime

If a deterministic address is needed (e.g. based on device serial number), it can be set before `bt_enable()`:

```c
bt_addr_le_t addr = {
    .type = BT_ADDR_LE_RANDOM,
    .a    = { .val = { 0xC0, 0xFF, 0xEE, 0x01, 0x02, 0xC3 } },
    /*                                               ^^-- bits 47:46 must be 11 */
};
bt_id_create(&addr, NULL);
bt_enable(bt_ready);
```

> **Note:** Bits 47 and 46 of a Random Static Address must both be `1`. The example above uses `0xC3` as the most-significant byte (`1100 0011`), satisfying this requirement.

## Does the Address Change on Every Flash?

**Without `CONFIG_BT_SETTINGS=y`** (default / current state of the samples):

- The address is generated at runtime from `sys_rand_get()` — a new value on every boot.
- Every reset and every `west flash` produces a different address.
- Home Assistant / bthome-logger will treat the device as a **new, unknown sensor** after each reboot.

**With `CONFIG_BT_SETTINGS=y`**:

- The address is generated once and written to the NVS flash partition.
- `west flash` (without `--erase`) only writes the application image — the NVS partition is **not touched** → address stays the same across reflashes.
- A full chip erase (`west flash --erase` or `nrfjprog --eraseall`) wipes NVS → a new address is generated on next boot.

Required Kconfig additions for stable addresses:

```kconfig
CONFIG_BT_SETTINGS=y
CONFIG_SETTINGS=y
CONFIG_NVS=y          # or CONFIG_ZMS=y on newer NCS versions
CONFIG_FLASH=y
CONFIG_FLASH_PAGE_LAYOUT=y
CONFIG_FLASH_MAP=y
```

## Summary for BThome Nodes

- Without `CONFIG_BT_SETTINGS`, the address changes on every reboot — **not suitable for production**.
- Add the settings stack (see above) to get a stable address across normal reflashes.
- Use `BT_LE_ADV_OPT_USE_IDENTITY` in all advertising parameter structs so the hub always sees the same MAC.
